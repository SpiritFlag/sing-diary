## 6. 회고 (Lessons Learned)

### 6.1 잘된 것 (Keep)

- **문서를 실시간으로 개정하며 진행**: Design §3.4가 프로덕션 장애를 겪을 때마다 즉시 개정(v0.1→v0.4)돼, 문서와 코드가 끝까지 어긋나지 않았다.
- **실 DB 대상 테스트**: 처음부터 Vitest를 로컬 mock이 아닌 실 Postgres(Neon)로 돌린 덕에, 부분 유니크 인덱스·CHECK 제약 같은 DB 레벨 불변식을 진짜로 검증할 수 있었다.
- **브라우저 수동 QA가 실제로 버그를 잡음**: L2/L3를 Playwright 대신 수동으로 대체하기로 한 결정이 결과적으로 옳았다 — 두 개의 실제 크래시(ws 힙 예외, song 필드 누락)를 다 이 경로에서 발견했다.
- **Vercel 로그를 직접 읽는 습관**: "Digest만으로는 원인을 모른다"는 정직한 인정 후 Vercel CLI 로그인까지 해서 실제 스택트레이스를 확인한 게 두 번의 프로덕션 장애 진단에 결정적이었다.

### 6.2 개선 필요 (Problem)

- **Design §8 "실 Neon 브랜치"를 처음부터 안 지켰다.** 테스트 DB 분리를 계획만 하고 실제로 만들지 않은 채 module-2부터 여러 세션 동안 단일 DB로 테스트를 돌렸고, 그게 프로덕션과 같은 DB라 실사용 데이터가 반복적으로 삭제됐다. **사용자가 직접 발견하기 전까지 인지하지 못했다.**
- **git add에 글롭 패턴을 쓰다가 커밋을 통째로 놓칠 뻔했다** (`(app)` 괄호 디렉터리) — module-4에서 rename만 커밋되고 실제 파일들이 누락된 채 커밋된 사례.
- **인프라 우회 수단을 과소평가하고 과대평가하는 걸 반복했다**: Clerk도 "dev 인스턴스면 되겠지"라고 가정했다가 인스턴스별 서명 도메인이 다르다는 걸 뒤늦게 알았다. 반대로 초기엔 curl 핸드셰이크 한계를 "당연히 못 뚫는다"고 단정했다가, 결국 sign-in token 리딤으로 뚫어냈다 — 가정하지 말고 먼저 실측했어야 했다.
- **로컬 컴파일이 서버(Lightsail)에 부하를 준다는 사실을 사용자가 알려주기 전까지 인지하지 못하고 `next build`/`next dev`를 반복 실행했다.**

### 6.3 다음에 시도할 것 (Try)

- **사이클 시작 시점에 "테스트 DB는 앱 DB와 물리적으로 분리"를 Do의 module-2 체크리스트 첫 항목으로 강제**한다 — Design에 적어두는 것만으론 부족했다.
- **인프라(Vercel/Clerk/Neon) 관련 가정은 실측 전에는 결론 내리지 않는다** — "안 될 것 같다"도 "될 것 같다"도 5분짜리 curl/스크립트로 먼저 확인.
- **`git add` 시 디렉터리 글롭 대신 `git status --short` 결과를 직접 확인 후 파일 단위로 스테이징**하거나, add 직후 항상 `git status`로 재확인한다.
