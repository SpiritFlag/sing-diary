# expand-fill-queue 계획서

> **요약**: 직전 사이클이 "번호 입력을 건너뛰고 추가"를 세 분기 모두에 열어 결손을 만드는 정식 경로를 냈다. 그 결손을 회수할 빈칸채우기 큐(ARCHITECT §5.6)를 세운다. 곁들여 곡 관리 표에 남은 잔손질 두 건을 같이 친다.
>
> **프로젝트**: sing-diary
> **버전**: v1.2.0
> **사이클**: expand-fill-queue
> **작성일**: 2026-08-23
> **상태**: Draft

## Executive Summary

| 관점 | 내용 |
| --- | --- |
| **문제** | **결손을 만드는 문만 열려 있고 거두는 문이 없다.** 직전 사이클(expand-playlist-import)이 ARCHITECT §5.2 세 분기 모두에 "번호 입력을 건너뛰고 추가"를 넣었다. 그것은 결함이 아니라 의도된 설계다 — §5.2가 "결손은 빈칸채우기 큐가 회수한다"고 적어뒀기 때문에 건너뛰기를 허용할 수 있었다. **그 큐가 아직 없다.** 지금 회수 수단은 곡 관리 표에서 전체 목록을 눈으로 훑어 찾아 고치는 것뿐인데, 표는 "전부"를 보여줄 뿐 "채워야 할 것만 골라 순서대로"가 아니다. |
| **해결** | ARCHITECT §5.6의 큐 A(번호 결손, 브랜드별)·큐 B(메타 결손, title/artist NULL) 두 쿼리를 `SongQuery` 포트에 신설하고, **한 화면 세 탭**(TJ 번호 / KY 번호 / 제목·아티스트)으로 한 건씩 순차 제시한다. 저장은 **기존 배관을 그대로 재사용**한다 — `setNumber`·`clearNumber`·`updateMeta`와 그 위의 라우트 3개가 이미 있다. 쓰기가 3~4초인 이 프로젝트의 상수를 정면으로 맞기 때문에 **낙관적 갱신으로 즉시 다음 건**으로 넘어간다. |
| **기능/UX 효과** | 집에서 PC를 열면 "TJ 12건 · KY 3건 · 메타 8건"이 배지로 보인다. 탭 하나를 골라 번호를 치고 저장을 누르면 **기다리지 않고 바로 다음 곡**이 뜬다. 현장에서 건너뛴 곡들이 그날 저녁에 회수된다. |
| **핵심 가치** | ARCHITECT §7 M3의 몸통이자 §2 설계 원칙 2("현장 입력은 최소, 정리는 사후에")의 나머지 절반이다. 지금까지 이 서비스는 "최소 입력"만 있고 "사후 정리"가 없었다. **有始有終(유시유종)** — 벌여둔 계약은 갚아야 한다. |

## Context Anchor

| Key | Value |
| --- | --- |
| **WHY** | 결손 생산 경로를 먼저 열어놓은 상태다. 회수자가 따라붙지 않으면 결손이 눈덩이가 되고, 그 순간 "건너뛰고 추가"를 허용한 §5.2 결정 자체가 잘못이 된다. **本末顚倒(본말전도)를 이번에 바로잡는다.** |

| **SUCCESS** | 큐 세 탭이 각각 §5.6 쿼리대로 대상을 뽑고, 한 건 저장하면 그 곡이 큐에서 빠지며, 저장 실패 건이 유실 없이 큐로 돌아온다. 기존 L1 28케이스 회귀 0. 3-state 계약(행 없음 / UNSUPPORTED / AVAILABLE) 무손상. |
| **SCOPE** | 큐 읽기 포트·유스케이스 → 큐 화면 셸(탭·잔여 배지·빈 상태) → 큐 A 번호 입력 → 큐 B 메타 입력 → 낙관적 연속 저장과 실패 회수 → 곡 관리 표 잔손질 2건 → L1 확장·Preview 실측 |

## 1. Overview

### 1.1 목적

ARCHITECT §7 마일스톤 M3의 첫 덩어리 — **§5.6 빈칸채우기 큐 A·B** — 를 구현한다. 그 과정에서 곡 관리 표에 남은 백로그 두 건(`80c2fe1d` 저장 중 셀 피드백, `47765514` 표 내부 검색 방식 무기록 변경)을 같이 처리한다.

M3의 나머지 두 항목(**일괄 입력**, **공개 설정**)은 이번 범위가 아니다 — 사유는 §2.2.

### 1.2 배경

**직전 사이클이 이 사이클을 불렀다.** expand-playlist-import는 §5.2 브랜드 변환 3분기를 열면서 세 분기 모두에 "번호 입력을 건너뛰고 추가"를 넣었다(사용자 결정, ARCHITECT §5.2 원문). 그 report §4.1이 스스로 적어놨다:

> **M3 빈칸채우기 큐(`002e953e`) 시급성 상승** — "건너뛰고 추가"가 세 분기 모두에서 열렸다. 번호 없는 entry가 이번 사이클부터 흔해진다(의도된 설계). 회수 수단은 현재 곡 관리 표뿐. **우선순위 High**

**결손의 출처가 셋으로 늘었다.** ① first-take의 stub 생성(현장 번호 입력 시 title NULL로 곡이 생긴다) ② 곡 관리 표 인라인 수정에서 비워둔 값 ③ **직전 사이클의 "건너뛰고 추가"**. 앞의 둘은 부산물이었지만 셋째는 사용자가 현장에서 의도적으로 만드는 것이고, 앞으로 가장 흔한 출처가 된다.

**반대로, 이 사이클은 배관 신설이 거의 없다.** 저장 쪽은 직전 두 사이클이 이미 다 깔아뒀다(§1.3-2). 이번에 새로 짓는 것은 **"무엇을 채울 차례인가"를 고르는 읽기 경로와 그것을 한 건씩 내놓는 화면**뿐이다. 그래서 스키마 변경이 0건이고, 어쩌면 신규 API 라우트도 0건이다(§1.3-6 ★).

**곡 관리 표 잔손질 둘을 같이 묶은 이유**는 접점이 같아서다. 큐의 입력 UI는 표의 `NumberCell`·`InlineCell`이 하는 일과 같은 일을 하고, 큐 화면을 지으면서 `SongTable.tsx`를 어차피 열게 된다. 따로 하면 같은 파일을 두 번 읽는다(`cycle-propose` 안 1의 묶음 근거).

### 1.3 착수 전에 코드로 확인한 것

Plan 단계에서 실제 파일을 열어 확인한 사실이다. 추정이 아니므로 Design은 여기서 출발한다.

1. **큐가 쓸 쿼리 두 개는 ARCHITECT §5.6에 SQL로 이미 적혀 있고, 그 자리가 포트에 비어 있다.**
   `src/application/ports/song-query.ts`의 `SongQuery`는 `search` / `list` / `findById` 셋뿐이다. 큐용 메서드는 신설이다. 다만 **스키마 변경은 0건**이다 — §5.6의 두 쿼리는 지금 있는 `songs` · `song_numbers` 와 `idx_songs_owner`만으로 돈다.

2. **★ 저장 배관을 새로 만들 필요가 전혀 없다.**
   | 큐가 할 일 | 이미 있는 것 |
   | --- | --- |
   | 번호 확정(AVAILABLE) | `SongRepo.setNumber` → `useCases.setSongNumber` → `PUT /api/songs/:id/numbers/:brand` |
   | 미지원 표시(UNSUPPORTED) | 같은 경로, `{status:"UNSUPPORTED"}` |
   | 번호 지우기(행 없음) | `SongRepo.clearNumber` → `useCases.clearSongNumber` → `DELETE` 같은 경로 |
   | 제목·아티스트 채우기 | `SongRepo.updateMeta` → `useCases.updateSongMeta` → `PATCH /api/songs/:id` |
   이 사이클은 **네 번째 쓰기 경로를 만들지 않는다.** 기존 셋을 새 화면에서 부를 뿐이다. 3-state 계약이 자동으로 지켜지는 이유가 이것이고, 직전 사이클이 `addEntryBySong`에서 쓴 것과 같은 수법이다(그 report D-S).

3. **★ 세 유스케이스가 전부 확정값(`SongListItem`)을 돌려준다.**
   `update-song-meta.ts` · `set-song-number.ts` 셋 다 `tx.run(...)` 뒤에 `query.findById()`로 다시 읽어 반환한다. 즉 **낙관적 갱신이 필요로 하는 "서버 확정값"이 이미 응답에 실려 온다** — 별도 재조회 라운드트립이 없다. 다만 이는 저장 1건이 **쓰기 1회 + 읽기 1회**임을 뜻한다(§3.2 응답성의 근거).

4. **`findByIdForOwner`의 주석이 이 사이클에 못을 박아뒀다.**
   ```
   // updateMeta/setNumber의 touch와 달리 부수효과가 없다 — 조회일 뿐이므로 updated_at을
   // 건드리지 않는다(M3 빈칸채우기 큐가 updated_at을 신선도 신호로 쓴다).
   ```
   직전 사이클이 이 사이클을 위해 남긴 배려다. **그런데 그 약속을 받아 쓸지는 아직 정해진 바 없다** — 큐 정렬에 `updated_at`을 쓰면 한 건 저장할 때마다 그 곡이 목록 맨 끝으로 튀어 순서가 흔들린다(§5 R2와 직결). Design에서 정한다.

5. **`SongTable`의 "저장 중 잠금"은 실재하고, 피드백만 부실하다.**
   `commitCell` 첫 줄이 `if (isPending(key)) return;`이고 각 셀에 `disabled={isPending(...)}`가 걸려 있다. 시각 피드백은 `disabled:opacity-50` 하나뿐이다(`NumberCell`·`InlineCell`). **백로그 `80c2fe1d`는 잠금 로직이 아니라 표시의 문제다** — 고칠 대상이 좁다.

6. **★ 표 내부 검색은 클라이언트 substring 필터다.**
   `SongTable.matchesFilter`가 `title/artist/memo`를 이어붙여 `includes()`한다. 통합검색 API(`/api/songs/search`)를 부르지 않는다. 백로그 `47765514`가 지적한 Plan→Design 무기록 변경 그대로다. **이것은 코드를 고칠 일이 아니라 결정을 기록할 일이다** — 현 규모에서 결과가 동일하고, 표는 이미 전체 목록을 로드해두기 때문이다.

7. **★ 이 사이클은 신규 API 라우트가 0건일 수 있다.**
   `src/app/(app)/songs/page.tsx`가 선례다 — RSC에서 `useCases.listSongs(ownerId)`를 직접 부르고 API를 경유하지 않는다. 큐 목록도 같은 방식이면 신규 라우트가 필요 없고, 저장은 §1.3-2의 기존 라우트 셋을 쓴다. **그러면 L1에 새로 넣을 "신규 엔드포인트" 케이스가 없다** — 대신 기존 라우트를 큐 시나리오(연속 저장·실패 복구·3-state 전이)로 돌리는 케이스를 넣어야 한다. Design에서 확정한다.

8. **판정 순수 함수가 이미 있고, 큐가 그대로 쓴다.**
   `song-state.ts`의 `commitDecision(draft, touched)`이 "안 건드림 / 지우고 확정 / 번호 확정"을 판정한다. 큐의 번호 입력도 같은 판정이 필요하다 — **재사용이지 신설이 아니다.** 다만 큐에는 표에 없는 조작이 하나 더 있다(건너뛰기), 그 판정을 같은 모듈에 넣을지는 Design 판단이다(컨벤션 C-6).

9. **곡이 0건인 경우를 표는 이미 다룬다.** `SongTable`이 "등록된 곡이 없어요" / "일치하는 곡이 없어요" 두 빈 상태를 구분해 낸다. 큐도 "채울 것이 없다"는 상태가 필요하고, 그것은 **축하할 상태**이지 오류가 아니다.

## 2. Scope

### 2.1 In Scope

**A. 큐 읽기 경로 (ARCHITECT §5.6, 백로그 `002e953e`)**

- [ ] `SongQuery`에 큐 A(번호 결손, 브랜드 인자) 조회 메서드 신설 — §5.6 `LEFT JOIN ... WHERE n.song_id IS NULL`
- [ ] `SongQuery`에 큐 B(메타 결손) 조회 메서드 신설 — §5.6 `WHERE title IS NULL OR artist IS NULL`
- [ ] 유스케이스 신설 + `container.ts` 배선
- [ ] 세 탭의 **잔여 건수**를 함께 낸다 (배지 표시용)
- [ ] 스키마 변경 **0건** · 마이그레이션 **0건** (§1.3-1)

**B. 큐 화면 — 한 화면 세 탭 (사용자 결정)**

- [ ] `[TJ 번호] [KY 번호] [제목·아티스트]` 세 탭. 각 탭에 잔여 건수 배지
- [ ] 한 건씩 제시 (`3/12` 형태의 진행 표시)
- [ ] 탭 전환이 **재조회 없이** 끝난다 (한 번에 받아 클라이언트에서 나눈다)
- [ ] "채울 것이 없어요" 빈 상태 — 탭별 / 전체 (§1.3-9)
- [ ] `AppHeader`에 진입점 추가 (PC 정리 동선, ARCHITECT §6)
- [ ] 큐 A는 곡 식별자로 **번호가 아니라 제목·아티스트**를 보여준다 (번호가 없어서 큐에 온 것이므로)

**C. 큐 입력 조작**

- [ ] 큐 A — 번호 입력(→ AVAILABLE) / **미지원**(→ UNSUPPORTED) / 건너뛰기
- [ ] 큐 B — 제목·아티스트 입력 / 건너뛰기
- [ ] 저장은 기존 라우트 3개를 그대로 호출 (§1.3-2 — **신규 쓰기 경로 0건**)
- [ ] 판정은 `song-state.ts` 순수 함수로 (컨벤션 C-6, §1.3-8)
- [ ] **외부 검색 링크는 넣지 않는다** (사용자 결정 — §2.3에 미구현으로 명시)

**D. 낙관적 연속 저장 (사용자 결정 — 이 사이클의 위험 중심)**

- [ ] 저장을 누르면 **응답을 기다리지 않고 즉시** 다음 건을 띄운다
- [ ] 성공한 건은 큐에서 빠진다 (재조회 없이 클라이언트 상태로)
- [ ] **실패한 건은 유실 없이 큐 끝으로 돌아온다** + 토스트로 알린다 (★ R1)
- [ ] 건너뛴 건은 **이번 방문에서만** 큐 뒤로 밀린다 — 화면을 떠나면 초기화 (사용자 결정, 상태 저장 없음)
- [ ] 마지막 건을 처리한 뒤 아직 응답이 안 온 저장이 남아 있으면 그것을 기다린 뒤 결과를 정산한다

**E. 곡 관리 표 잔손질**

- [ ] 저장 중 셀의 시각 피드백 강화 — 백로그 `80c2fe1d` (§1.3-5. 잠금 로직은 **손대지 않는다**)
- [ ] 표 내부 검색이 클라이언트 substring 필터임을 **Decision Record에 기록** — 백로그 `47765514` (§1.3-6. 코드 변경 없음). 페이지네이션이 필요해지는 시점을 재검토 조건으로 함께 적는다

**F. 검증**

## 5. Risks and Mitigation

| # | 위험 | 영향 | 가능성 | 완화 |
| --- | --- | :-: | :-: | --- |
| **R1 ★** | **낙관적 이동에서 실패 건이 조용히 사라진다.** 화면은 이미 다음 곡인데 저장이 실패하면 사용자가 방금 친 번호의 행방을 모른다. 결손을 회수하러 온 화면이 결손을 새로 만드는 셈 | **High** | Medium | 저장 in-flight를 곡 id로 추적하고, 실패 시 **입력값까지 함께** 큐 끝으로 복귀시킨다(빈 카드가 아니라 친 값이 살아 있어야 한다). 토스트에 곡 식별자를 싣는다. FR-11을 DoD의 별도 항목으로 세워 실측으로 닫는다 |
| **R2 ★** | **큐 목록을 언제 다시 읽는가.** 저장할 때마다 재조회하면 매 건 3~4초가 더 붙고 인덱스가 어긋난다. 반대로 스냅샷을 고정하면 다른 탭·다른 창에서 생긴 변화를 못 본다 | High | High | **입장 시 한 번 읽고 스냅샷으로 고정**, 이후 큐 상태는 클라이언트가 관리한다(성공=제거, 실패=끝으로, 건너뛰기=뒤로). 다시 읽는 것은 사용자가 명시적으로 새로고침할 때뿐. 이 결정을 Decision Record에 남긴다 |
| **R3 ★** | **한 곡이 여러 탭에 동시에 뜬다.** TJ·KY 둘 다 없고 제목도 NULL인 stub 곡은 세 탭 전부에 등장한다. 한 탭에서 처리해도 다른 탭에 남아 "왜 또 나오나" 싶다 | Medium | **High** | 이것은 결함이 아니라 §5.6 쿼리의 정의다(큐 A는 브랜드별, 큐 B는 메타). 다만 **같은 곡을 두 번째로 만났을 때 그 사실이 보여야** 한다 — 카드에 다른 탭에서 방금 채운 값을 함께 띄우는 정도로 완화. Design에서 확정 |
| **R4** | **낙관적 UI가 4초 단가를 가릴 뿐 없애지 않는다.** 20건을 몰아 채우면 화면은 끝났는데 뒤에서 80초어치 요청이 밀린다. 브라우저 동시 연결 한도에 걸리거나 페이지를 떠나면 유실된다 | Medium | Medium | 동시 in-flight 상한을 두고, 미완료 저장이 남은 채로 화면을 떠나려 하면 경고한다(FR-13). 근본 해결은 백로그 `baea17b1` — **이번 범위 밖임을 report에 명시** |
| **R5** | **`SongTable` 회귀.** 잔손질 두 건 때문에 표를 여는데, 거기엔 직전 사이클의 셀 단위 레이스 수정(G-3)과 `pendingRef` 구조가 들어 있다. 스타일 하나 고치려다 저장 로직을 흔들 수 있다 | High | Low | **컨벤션 C-7 방식을 그대로 쓴다** — `commitCell`·`writeCell`·`extractField` 세 함수는 diff에 나타나지 않는 것을 약속으로 걸고 Check에서 diff로 검증한다. FR-16은 표시 계층(`NumberCell`·`InlineCell`)에서만 처리 |
| **R6** | **`updated_at`을 큐 정렬에 쓰면 순서가 흔들린다.** `updateMeta`·`setNumber`가 touch하므로 한 건 저장할 때마다 그 곡이 정렬 맨 끝으로 튄다 | Medium | Medium | 큐 정렬은 **표와 같은 기준**(title NULLS FIRST → artist NULLS FIRST)을 기본으로 검토하고, `updated_at`을 쓴다면 스냅샷 고정(R2)이 이미 흔들림을 막는다는 것을 근거로 남긴다. `findByIdForOwner` 주석의 약속은 유효하되 **이번에 꼭 소비해야 하는 것은 아니다** |
| **R7** | **신규 API 라우트가 0건이면 L1이 검증할 새 엔드포인트가 없다**(§1.3-7). 자칫 "L1 통과"가 큐를 하나도 안 본 채 나올 수 있다 | Medium | Medium | L1 신규 케이스를 **엔드포인트 단위가 아니라 시나리오 단위**로 짠다 — "번호를 채운 뒤 큐 A 조회에서 그 곡이 빠졌는가"처럼 큐 쿼리의 결과를 직접 대조한다. 그러려면 큐 조회를 API로도 낼 것인지가 Design 결정 사항이 된다 |
| **R8** | 큐가 비었을 때(축하할 상태)를 오류처럼 보이게 만든다 | Low | Medium | `SongTable`의 두 빈 상태 구분 선례를 따른다(§1.3-9). "다 채웠어요"와 "아직 곡이 없어요"는 다른 말이다 |

first-take Design §2.0에서 클린 아키텍처 B안을 택한 이래 유지 중이다. 이번 사이클은 그 구조를 **소비**할 뿐 바꾸지 않는다.

### 7.2 주요 결정 (기존 승계, 신규 선택 없음)

| 항목 | 채택 | 승계 근거 |
| --- | --- | --- |
| 프레임워크 | Next.js 15 App Router | ARCHITECT §1 |
| 읽기 경로 | Neon HTTP 드라이버(`db`) | first-take Design §3.4 D-C. 큐 조회는 읽기 전용이므로 이쪽 |
| 쓰기 경로 | `pg` Pool + `TransactionRunner` | 같음. 큐는 기존 유스케이스를 통해서만 쓴다 |
| 상태 관리 | 컴포넌트 로컬 + 낙관적 갱신 | `SongTable` D-G 선례. 큐도 같은 계열이나 **큐는 목록 자체가 소모품**이라는 차이가 있다(R2) |
| 화면 데이터 공급 | RSC에서 유스케이스 직접 호출 | `songs/page.tsx` 선례(§1.3-7). 신규 API 라우트 필요 여부는 Design 결정 |
| 스타일 | Tailwind · 다크 파스텔 | ARCHITECT §1 |
| 테스트 | vitest(유닛) + `run-l1.mjs`(API 실측) | 로컬 RAM 1.9GB 제약상 Playwright 없음 |

### 7.3 Design에서 결정할 것 (★)

1. **큐 조회를 API로도 낼 것인가** — RSC 직접 호출만으로 충분한가, L1 검증 가능성(R7)을 위해 라우트를 낼 것인가
2. **큐 스냅샷의 수명** (R2) — 재조회 시점을 어디까지 사용자 조작으로 미룰 것인가
3. **큐 정렬 기준** (R6) — `updated_at`을 쓸 것인가, 표와 같은 기준을 쓸 것인가
4. **중복 등장 곡의 표시** (R3) — 세 탭에 걸친 같은 곡을 어떻게 알릴 것인가
5. **`commitDecision` 재사용 범위** — 큐의 판정을 같은 모듈에 넣을 것인가(C-6)
6. **in-flight 상한과 이탈 경고** (R4) — 몇 건까지 동시에 날릴 것인가
